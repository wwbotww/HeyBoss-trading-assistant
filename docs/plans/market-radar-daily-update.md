# 市场雷达每日更新完善方案

编写日期：2026-09-30。检查基线：`e2422b6`，业务代码基线为 `6b753c8`。状态：**用户已确认；M1–M3 已完成，M4 迁移、首次真实六来源及正式网页通过，连续两个自然计划日待验收**。

本文解决雷达未自动采集、任务状态不可见、数据陈旧提示不足和页面不自动重读的问题。依据为[项目事实源](../project-context.md)、[市场参考](../reference/market-radar.md)、[同步指引](../operations/market-radar.md)、当前实现及本机正式市场库。本文保留已批准的实施边界；实际验收结论另记录，不能将计划条目当作通过证据。

## 1. 目标与范围

让市场雷达在本机与 Docker 正常运行期间，每天自动完成所需采集、校验、计算、发布和网页展示。机器休眠、断网或容器重启后能恢复当前所需更新；页面能说明最后成功时间、目标日期、失败原因和下一次尝试时间。

范围包含固定价格池、当前市场宽度、宏观象限、盈利修正及观察股财报、观察股基本面、经济事件六条现有链路。沿用现有指标和来源契约，不扩展为盘中实时行情、历史 PIT 回填、综合交易评分或消息推送。

雷达是独立只读业务域。此次实施不修改 FacDigger，不修复或重启交易节点，不调用券商、审批或下单接口，不把雷达更新纳入 826 交易就绪条件。9 月 30 日发现的交易节点退出属于另一项工作，不能用本方案的完成代替其恢复验收。

### 2.3 不能只加一个定时器的原因

1. **生产 Catalog 写入冲突。** 雷达价格、宽度、宏观与 paper 数据服务当前指向同一 Catalog。现有文件锁只保护具体读写区间，等待上限 50ms，不负责整轮任务排队。宽度涉及数百标的，不能靠两个定时任务错开几分钟保证安全。
2. **成功状态不证明跟上目标日期。** 当前服务可对读取到的最后一日计算并发布 `COMPLETE`；供应商仍返回旧数据时，自动任务必须识别“尚未取得目标日”，不能以退出码 0 判定更新完成。
3. **存在审计前的失败窗口。** 宽度和盈利在创建 `sync_runs` 前获取成员；配置、认证或成员获取失败，可能没有来源运行记录。自动任务需要记录这次尝试为什么未能进入业务同步。
4. **缺少中断恢复依据。** 没有每日任务去重、跨重启重试预算、进程心跳和未完成任务收尾。仅依靠内存中的上次运行日期会在重启后重复采集。
5. **网页刷新机制不足。** 查询全局设置了 `refetchOnWindowFocus: false`，雷达没有轮询，事件窗口不会在跨 UTC 午夜时主动刷新。后端发布新数据后，长期打开的页面仍可能保留旧响应。
6. **新鲜度与完整性混淆。** 价格指标的 `complete` 只说明历史足够，当前没有明确的目标交易日陈旧判断；宽度主要检查成员年龄，不能充分说明价格日期是否落后。新鲜度、同步是否按时完成、指标能否计算应分别展示。

## 3. 推荐架构：独立雷达写入域与固定每日服务

### 3.1 为雷达隔离物理 Catalog

推荐继续共用现有采集和计算代码，但让雷达写入独立目录：

| 用途 | 拟采用的宿主路径 |
| --- | --- |
| 交易 Catalog | `runtime/catalog/eodhd`，保留现状 |
| 雷达 Catalog | `runtime/market-radar/catalog/eodhd` |
| 雷达数据库 | `runtime/market-radar/data/market-radar.db` |
| 雷达报告 | `runtime/market-radar/reports` |

雷达容器只挂载自己的三个目录，不再获得交易 Catalog、live/backtest 数据库或报告目录的写权限。Web 额外挂载雷达数据库目录为只读；现有交易与回测查询保持原装配。

增加 `MARKET_RADAR_CATALOG_PATH`，雷达入口不再回退使用通用 `CATALOG_PATH`。继续使用 `MARKET_RADAR_DATABASE_URL` 和 `MARKET_RADAR_REPORT_ROOT`，统一六个入口的宿主默认值和 Compose 路径。检查解析后的绝对路径，拒绝已知的生产 Catalog 或 live/backtest 数据库别名；Docker 挂载同时提供实际权限边界。

这是对当前“雷达与交易共用物理 Catalog”规则的明确调整，须随本方案确认后实施，并在验收后更新事实源。保持 NT Instrument、BarType、价格口径和供应商适配一致，不承诺不同采集时刻得到逐字节相同的数据。

选择这一方式的理由是：共享写入协调还需要改造 paper 服务的所有权和优先级，并处理它等待晚到因子期间的让出规则；把雷达放入 paper 循环又会使数百标的采集影响交易输入时限。独立目录只调整雷达装配，代价是少量重合标的的重复存储和请求，需要在首次运行时核算实际配额。

目录隔离不等于供应商配额隔离。若 FacDigger、paper 和雷达共用 EODHD 额度，首次上线必须同时核算现有生产消耗及雷达重建/重试成本；额度不足时暂停雷达自动采集并记录阻塞，不能靠反复重启消耗交易数据准备所需额度。

不新增通用调度框架、插件、Redis、Celery 或第三方依赖，也不新增与现有价格管道相似的第二套实现。

### 3.2 单一写入者

新增 `market-radar-daily` Compose 服务，只接收 EODHD/FRED 凭据和雷达路径，不依赖 IB Gateway、TradingNode 或 Bot。采用 `restart: unless-stopped`；其重启只恢复数据采集。

每日服务在整个生命周期持有雷达目录中的进程文件锁。六个维护 CLI 也必须获取同一组资源锁；每日服务运行时，手动同步明确拒绝执行。人工维护只需停止雷达服务。沿用现有 Catalog 读写锁保护文件操作，两种锁分别解决“只能有一个同步进程”和“不能读取半次写入”。

采用单进程、固定顺序、逐来源执行，不并发启动多个来源任务。长任务执行期间仍维护心跳；不在数据库事务内等待网络，不为心跳长期占用 SQLite 写锁。

## 4. 调度、日期与补跑规则

### 4.1 默认时间与配置

新增 `config/market-radar-daily.yaml`，与金融指标配置分开。建议默认值：

| 参数 | 默认值 | 用途 |
| --- | --- | --- |
| `run_at_utc` | `06:00` | 每个 UTC 日的计划时刻 |
| `poll_interval_seconds` | `60` | 检查到期、恢复及更新心跳 |
| `retry_interval_seconds` | `3600` | 来源级失败后的再次尝试间隔 |
| `max_attempts_per_day` | `4` | 同一任务、同一计划日最多四次完整尝试 |

06:00 UTC 是工程默认值，不是供应商准时发布承诺。现有 EOD Bar 的 `ts_init` 位于数据日期的 UTC 日末，管道会过滤尚未到可用时间的 Bar，因此不采用“美股收盘后立即运行”的简单方案。供应商晚到通过日期门禁和有限重试处理。

交易日继续经 `data/market_calendar.py` 的最小接口查询 `exchange_calendars/XNYS`，雷达不直接引入第三方日历类型，也不复用带交易业务含义的 `expected_factor_date()`。

### 4.2 三个日期分开记录

- **计划日 C**：最近一个已经到达 06:00 UTC 的日历日期。
- **目标价格日 D**：严格早于 C 的最近一个 XNYS 常规交易日。
- **实际采集日 Q**：本次真正开始采集的 UTC 日期，用于当前盈利、基本面与事件，不能伪写成离线期间的日期。

例如 2026-09-30 06:00 UTC 的价格目标为 9 月 29 日；9 月 28 日周一早上的目标为 9 月 25 日周五。周末和休市日沿用最近已应可用的交易日，不要求不存在的周末 Bar。夏令时和提前收盘由统一日历处理，计划时刻始终为 UTC。

价格新鲜度以此“当前已经到期的目标 D”比较，06:00 之前不提前宣布前一天收盘数据逾期。保留实际数据日期和采集时刻，不能把采集时间当成价格时间。

### 4.3 六条任务的执行与依赖

执行顺序为价格、宏观、经济事件、基本面、盈利、宽度；先处理常用与较轻来源，把数百成员的宽度任务放在最后。一个来源失败后继续检查其他独立来源。

| 任务 | 调度规则 | 完成本轮需要证明的事实 |
| --- | --- | --- |
| 固定价格池 | 目标 D 尚未成功覆盖时运行 | SPY 基准到 D；固定池覆盖与单项缺失如实披露；目标日缺价与指标历史不足分别处理 |
| 宏观 | 新目标 D 或该目标尚未完成时运行 | 四条价格在 D 对齐；FRED 按既有向后对齐和有效性规则处理 |
| 经济事件 | 每个计划日运行，含周末 | 实际 Q 的合法批次已发布，覆盖查询所需日期；空批次可以成功 |
| 基本面 | 每个计划日运行，含周末 | 完整观察池在实际 Q 采集；季度未变化、单项合法缺失不等于任务失败 |
| 盈利与财报 | 每个计划日运行，含周末 | 实际 Q 的成员、分类、Trends、观察股财报整批通过并发布 |
| 当前宽度 | 新目标 D 或该目标尚未完成时运行 | 雷达 Catalog 中 SPY 已到 D；成员日期不晚于 D 且不超过既有七日界限；指标覆盖如实披露 |

宽度依赖本域的 SPY 基准；不能在价格任务失败时悄悄沿用更旧基准计算“今日宽度”。依赖未就绪记为等待，不消耗宽度的远端请求重试次数。宏观自行同步四条输入；盈利自行取得成员，不依赖宽度成功。

正常休市期间，已覆盖 D 的价格和宽度不重复下载全市场。宏观若因 FRED 晚到而未完成，仍可对相同 D 继续有限尝试；不得把“价格没产生新交易日”当作忽略待到数据的理由。成员来源如果已经推进到目标 D 之后，不回填伪历史成员，记录等待下一可匹配目标。

`COMPLETE`、`partial` 和 `stale` 不合并：完整执行可发布合法部分指标，但页面仍需展示覆盖与不可用原因；不足覆盖不能算“全部指标可用”。自动运行增加明确的目标日期检查，基准旧价格返回 `waiting_source`，保留上一份已发布快照。固定池基准已到 D、个别标的缺 D 时可沿用原语义发布带缺失的部分快照，但本轮记为等待来源并有限重试；已有 D 价格、仅指标历史不足则记为完成并披露退化。这样不删除合法部分数据，也不以部分更新结束所有补数尝试。

### 4.4 冷启动与休眠恢复

雷达新 Catalog 由现有管道从供应商重建，避免在线复制正在被 paper 修改的目录。价格和宽度显式请求足够覆盖指标的 400 个日历日；宏观沿用四年窗口。重建只补价格历史，现有当前成员、盈利、基本面和经济事件不提供历史 PIT 回填。

启动检查必须确认雷达 Catalog 已初始化并能安全读取必要基准；复制来的市场数据库有成功快照，不证明新的 Catalog 已经准备好。当前日期已满足但 Catalog 为空时，仍需完成历史初始化后才能进入正常增量模式。

每日更新使用既有 `daily` 模式、十日重叠窗口及公司行动校验，禁止自动 `reconcile` 截断历史。新增成员按需要准备历史，样本不足保留原语义。检测到公司行动或历史修订导致现有序列不再可靠时保留质量失败，不放宽检查来完成任务。

启动或从休眠恢复后，根据数据库记录只追赶最近已到期的一轮，不逐日重放所有错过的任务。价格按缺口准备连续历史；当前快照只采集真实 Q。离线一个月也不会伪造一个月的盈利、基本面或事件历史。

在当日 06:00 之前恢复时，可以补最近已到期的上一计划日；当前快照仍记实际采集日。到新的计划时刻重新计算到期状态。若之前已在实际采集日成功取得当前来源，满足本轮所需范围时复用该成功结果，避免短时间重复请求。

系统时间倒退、未来采集时间、未经确认的写入标记或数据库损坏必须显示异常，不靠更改时钟、删除标记或重复覆盖旧库自行“修复”。机器关机期间不能采集；长期无人值守仍需要持续在线主机。

## 5. 最小运行状态与恢复设计

### 5.1 复用来源审计，新增两张有直接调用方的表

保留 `sync_runs` 与全部快照表的格式和含义，不增加 schema 版本、哈希链或通用任务队列。仅在市场数据库增加：

| 表 | 最小内容 | 必要性与调用方 |
| --- | --- | --- |
| `daily_sync_attempts` | `run_id`、固定任务名、计划时刻、目标日期、尝试序号、开始/结束、结果、脱敏原因、下次重试时刻 | 每日服务恢复、限次和 API 状态；覆盖进入 `sync_runs` 之前的失败 |
| `daily_sync_worker` | 固定单行、启动/心跳/停止时刻、当前任务、下一计划时刻、实际调度参数 | 空闲时也能判断采集进程是否在线；供只读 API 和容器健康检查 |

`daily_sync_attempts` 对“任务名、计划时刻、尝试序号”设唯一约束。它记录调度结果，不复制 Bar 计数、快照 payload 或整份供应商异常。尝试的 `run_id` 通过现有 `run_id_factory` 传给对应服务；如果前置校验失败，对应 `sync_runs` 可以不存在，不建立要求它预先存在的外键。

尝试结果使用 `running / complete / waiting_source / failed / interrupted`。是否还可重试由脱敏错误分类、次数和时间决定；“尚未到期”“依赖等待”“已由成功批次满足”由查询推导，不制造空的来源运行记录。

在有效配置与写锁检查后，先持久化尝试，再调用来源服务。缺凭据可以留下可解释的任务失败，但不能创建伪来源成功记录。每日服务外的单源 CLI 仍保留其原有“无效配置不创建业务运行”的边界，状态页同时展示最近单源维护结果。

新增表由显式初始化写入端的 `create_schema()` 创建，Web 不迁移。旧十四张表不改列；旧市场库的只读查询保持可用，新增状态接口在表尚未初始化时返回 `not_configured`。

### 5.2 失败分类与预算

- 连接中断、超时、临时 HTTP 错误：先使用现有请求级重试；耗尽后才进入来源级一小时重试，最多四轮。
- 目标价格未到或来源尚未对齐：`waiting_source`，有限重试，不发布伪新批次。
- 缺凭据、认证/权限拒绝、格式不符、非法身份或确定性质量错误：本轮停止自动重试，显示可操作原因；不按分钟反复请求。修复后重启仍保留预算和本轮停止状态；需立即验证修复时，停止每日服务后使用原单源 CLI，后续每日服务可以识别该次成功发布。
- 429 或配额不足：保留原始类别的脱敏代码，进入有限退避；不无限增大并发、不把每日预算清零。已停止自动尝试的来源保留可见状态。
- SQLite 损坏、无法记录结果、Catalog 中断标记：停止本写入进程或阻断相关价格任务，保留证据与已发布数据，不继续宣称健康成功。

价格管道有时把异常转换为 `PipelineSummary` 的质量项。分类需基于现有异常类型或稳定 issue code，不能靠解析带 URL 的异常字符串，也不能把所有 `data_quality` 都当成供应商暂时延迟。必要的类型化失败信息直接补到原管道结果，不另造同步实现。

失败按来源隔离；不得因为一个 FRED 请求失败而撤回已经成功的经济事件或基本面。Catalog 与数据库仍不承诺跨存储事务。

### 5.3 中断窗口与进程健康

进程取得唯一写锁后，才允许恢复本服务遗留的 `running` 尝试：

1. 对应来源已 `COMPLETE` 且快照满足本轮日期与覆盖目标：补齐尝试完成状态，不重新请求供应商；已发布合法部分数据但仍需补目标日缺价的，恢复为等待来源。
2. 对应来源仍 `RUNNING` 或尚未建立：记录中断，按预算和安全状态重新尝试；每次新尝试使用新 run_id，不改写旧失败成成功。
3. `.catalog-writing` 表明文件发布中断：保留标记，停止价格消费/写入并要求核对；禁止自动清标记。其他不使用 Catalog 的来源可以独立处理。

正常 SIGTERM 停止领取新任务，允许当前安全写入区间收尾；不能在已删除旧区间、尚未写完新区间时主动取消。强杀场景按上述恢复分支验收。容器可以自动重启，但不能以重启替代完整性检查。

每 60 秒更新一次心跳，查询距心跳超过 300 秒显示进程离线/失联。任务级退化与进程存活分别表达：供应商失败不等于进程死亡，心跳更新也不等于数据更新。健康检查只读取本地状态，不访问供应商或交易服务。

### 6.1 只读更新状态 API

新增 `GET /api/market-radar/sync-status`，返回：

- `observed_at_utc`、`worker_state`、`last_heartbeat_at_utc`、`next_scheduled_at_utc`。
- 六项固定任务的名称、目标日期、最近尝试、最近成功、已发布数据日期、已用次数、下次重试和脱敏原因。
- 采集是否完成、目标日期是否满足、指标是否退化分别保留，不设置一个掩盖部分失败的全站绿色成功位。

工作进程状态使用 `not_configured / running / idle / stopped / stale`；数据库损坏仍返回脱敏读取错误，不能返回 `not_configured` 掩盖故障。查询不依赖 Docker socket、供应商凭据或 live.db。

### 6.2 新鲜度契约

在价格摘要、板块集合和个股集合响应增加 `price_freshness`，至少包含 `expected_as_of_date`、`actual_as_of_date`、`lag_sessions`、`state`。状态区分 `fresh / stale / unavailable`。实际日期已安全可用且晚于计划要求的 D 时仍为 fresh，例如 06:00 前人工已采到前一交易日；只有尚未可用的未来日期或非法元数据才按错误处理。

查询复用 `schedule.py` 的日期规则；调度时刻读取 worker 保存的实际配置，尚未配置时使用同模块的明确默认值。该状态查询仍只读取市场库，Web 不加载每日采集器或请求供应商。

宽度同时披露成员年龄与价格是否到 D，不只检查成员七日阈值。保留宏观、盈利、基本面和事件现有来源新鲜度阈值；每日调度是否按时成功由更新状态表达，不把宏观三日阈值等改成统一“今天”。基本面季度未改变时可以每日采集成功，报告期仍显示原日期。

价格单项的 `validity` 继续说明计算完整性，不把有效历史数值清零。旧价格总览模块显示陈旧，保留数值及日期。个股和板块详情沿用已读取集合/摘要的新鲜度；不能在详情缺少日期的情况下独立宣称最新。

## 7. 网页使用方式

在现有雷达页添加简洁的“数据更新”区域，展示进程状态、最近成功和下一次计划；失败时展开来源及原因。产品文案使用“等待数据发布”“更新失败”“数据截至某日”等，不向普通页面暴露类名、文件锁、SQL 或容器细节。

雷达页处于可见状态时，每 60 秒重新读取当前视图需要的本地 API；隐藏标签页停止定时请求，重新可见、网络恢复和窗口获得焦点时重读。仅调整雷达查询策略，不改变账户、订单等页面的全局查询行为。

跨 UTC 午夜主动重新请求事件窗口和依赖日期的状态，仍由 API 决定十四日窗口，浏览器不计算交易日或改写事件日期。离开页面时清理监听与定时器；筛选和分页保留，已撤回事件的详情继续按既有规则关闭。

重新读取按钮始终只读数据库；没有采集或交易 POST。GET 失败与成功返回的陈旧快照继续分别展示；单个来源刷新失败不能清空其他成功来源。仅“后台运行中”不能覆盖该来源读取失败提示。

## 9. 迁移、上线与回退

1. 确认当前雷达无写入者。用 SQLite 备份接口把现有市场库保存到独立备份并复制到新雷达目录；核对完整性、六类最新快照、全部历史运行数量及时间。禁止复制运行中的 `.db` 文件来冒充一致备份。
2. 在新库显式创建新增运行表，验证旧记录不变。保留原市场库和原 Catalog，不删除 826 原始数据或其他业务数据。
3. 核对现有 EODHD/FRED 凭据权限、实际请求额度和首次重建成本。数百标的价格、拆股与分红请求不能按“一次任务就是一次 API”估算。沿用现有并发上限；先验证小范围解析，再在配额内跑完整目标池，不偷偷缩小宽度分母。
4. 从来源建立独立 Catalog，使用实际日期发布新批次；失败来源保留复制来的旧快照并明确陈旧原因。新成员不能被当作新的交易资格。
5. 调整 Web 的只读市场库挂载及环境变量，重建/重启受影响的 Web 服务。核对 API 的批次、日期、覆盖和运行状态与新库完全对应，避免 CLI 写新库而网页仍读旧库。
6. 显式启用每日服务，完成即时端到端验收和后续自然计划运行。实际市场库、网页数据和进程心跳都要有证据；只看到容器 Up 不算完成。

需要回退时只停止雷达每日服务并回退雷达/Web 装配，保留新库、Catalog 和报告用于排查。切回旧库只能作为明确的陈旧只读降级，不能覆盖新库或把旧数据宣布为更新成功。新增表为附加式，优先让旧读取逻辑继续读取新库的既有快照表；不在回退中修改任何交易审计。

## 10. 验收矩阵

| 场景 | 必须验证的结果 |
| --- | --- |
| 正常交易日 | 到计划时间产生所需任务；价格到 D，当前来源记 Q，快照与成功来源审计同事务发布 |
| 周末、节假日、提前收盘、夏令时 | D 来自既有日历；不存在周末价格需求；当前快照仍按日历日运行；固定 UTC 时刻不漂移 |
| 休眠数小时或多日、重启前后跨日 | 只补当前所需任务，价格补缺口，不伪造历史当前快照，不反复请求已满足目标 |
| 成功返回旧价格 | 日期门禁阻止伪新发布，状态为等待来源，按预算重试，旧快照仍有原始时间 |
| 固定池仅部分标的到 D | 可显示真实部分快照，但调度继续有限补数；指标历史不足与目标日缺价不混为一谈 |
| 宏观价格已到、FRED 晚到 | 单独显示宏观未完成/退化，不阻塞其他来源，不因 D 相同永久跳过重试 |
| 成员比目标价格新、基准未更新 | 不把不同日期强拼成今日宽度，不以删除成员提高覆盖率 |
| 单源暂时断网、429、认证失败、格式错误 | 分类正确；请求级与来源级重试均有界；次数跨重启保留；其他独立来源可发布 |
| 成员请求在来源审计前失败 | 每日尝试中有脱敏原因，页面不会表现为“从未尝试” |
| 服务提交后、调度记成功前崩溃 | 依据关联 run_id 和实际快照补齐状态，不重复采集 |
| 采集中或文件发布中强杀 | 正确记录中断；未完成文件标记保留；不读取或发布半次结果 |
| 同时启动两个每日进程或手动 CLI | 唯一锁拒绝第二写入者；失败不会生成第二份业务成功批次 |
| 与 paper 数据服务同时运行 | 使用隔离测试目录证明雷达不写生产 Catalog/live.db、不争用同一 Catalog 锁；不需要真实下单验收 |
| 旧十四表市场库升级 | 新表可显式创建，原快照/历史审计保持；只读 API 不建表；未配置状态不冒充在线 |
| 复制的市场库已有当日快照、新 Catalog 为空 | 初始化检查不误判可用；先准备必要价格历史，再进入正常增量 |
| 页面长期打开、后台切回、断网恢复、UTC 午夜 | 可见时自动读新批次；后台暂停；恢复和跨日正确重读；无供应商请求和写接口 |
| 价格陈旧但指标可算、合法空事件、部分基本面 | 日期、完整性、覆盖率、失败分别表达，不清零，不展示虚假全绿 |
| 新库切换和回退 | 正式 API/网页指向明确同一市场库；交易、回测与原始 826 数据保持完整 |

代码质量按项目要求执行 `ruff check`、`ruff format --check`、strict `mypy` 和完整 `pytest`，保持现有覆盖率门槛。前端执行生成契约检查、format、lint、typecheck、Vitest 与生产 build。新增测试重点验证上述恢复、跨日和写入边界，不为简单路径替换单独堆砌镜像实现的断言。

真实验收分两步记录：首次完整六来源采集及正式网页通过；随后至少两个连续计划日的自然运行，其中跨过一个新的价格目标日。另在隔离环境覆盖周末/节假日和中断恢复；不得为制造连续证据而调整正式时钟、回写采集时间或重置成功记录。

首次重建的耗时和配额单列，不冒充日常增量成本。供应商权限、覆盖或数据未到导致不能验收时，保留具体阻塞来源与重试事实；不得只用 fixture 宣称真实六来源已通过。

本方案建议一次确认以下实施方向：独立雷达写入目录与 Catalog、固定六任务常驻服务、06:00 UTC 默认计划、按目标日期恢复、两张最小运行表、只读状态接口和局部网页自动重读。新增依赖为零；这些变更均在 HeyBoss 内完成。

确认前只维护本文及文档入口。确认后按 M1 → M2 → M3 → M4 实施；如后续发现必须改变指标口径、共享交易代码行为或引入额外依赖，先补充方案再执行。

完成必须同时具备：每日服务可恢复地运行、真实来源按约定日期发布、故障与陈旧可解释、正式网页自动读到正确批次，以及雷达和交易的物理写入隔离。单次手工同步成功不等于本阶段全部完成。

## 12. 本轮实施补充

进程锁按实际数据库路径及 Catalog 路径分别持有两把 `flock`，取得全部锁后才能采集；这防止仅覆盖一个路径时产生两个写入者，仍是单进程固定六任务，不引入调度框架。Compose 隔离边界另由 `tests/test_project_structure.py` 验证。网页原有日期夹具按“已可用日线”规则更新，新增故障与可见性测试。

实际验收记录：[2026-09-30 雷达每日更新验收](../archive/market-radar-daily-acceptance-20260930.md)。后续两个自然计划日需真实观察，不能用模拟时钟代替。

本机真实验收发现 macOS 与 Docker Desktop 的 `flock`/POSIX 文件锁不互通，单靠内核锁不能满足跨环境唯一写入者要求。实现补充为同一 `runtime.py` 内独占创建 `.platform` 绑定，禁止异平台写同一目录；同平台仍用原进程锁，重启不需删除绑定或引入租约。真实调用方仍是七个入口，验收增加“容器运行时宿主锁探针拒绝、第二个容器拒绝且无新增尝试”。正式 Docker 数据用容器 CLI 维护，宿主 Python 使用独立运行目录。跨平台迁移需先停写再转入新目录。CLI 测试默认环境也统一放入 pytest 临时目录。

首次真实运行中宏观因缺少 FRED 凭据失败，其余五来源继续完成；用户配置凭据后，停止雷达、使用既有宏观维护入口发布，再恢复每日服务。原六次每日尝试保留，新增一次成功宏观来源审计；重启没有产生重复尝试。正式 API 和网页均显示六来源满足目标，盈利指标仍为合法部分覆盖。06:00 前不因跨 UTC 午夜重复采集已满足计划日的当前来源，早晨采得的同日批次可由新计划复用；此边界由隔离测试覆盖，未来自然运行仍需单独取证。
